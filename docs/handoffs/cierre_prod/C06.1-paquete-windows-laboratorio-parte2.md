## Hallazgo — `permisos.0011_ct02_identidad_revisiones` no puede aplicar sobre ninguna instalación real

```
django.db.utils.IntegrityError: could not create unique index "roles_cloud_id_key"
DETAIL:  Key (cloud_id)=(f40bff01-e910-4d2b-8d0e-3a4612f746fa) is duplicated.
```

`apps/permisos/migrations/0011_ct02_identidad_revisiones.py:15-19` y `:39-43`:

```python
migrations.AddField(
    model_name='rol', name='cloud_id',
    field=models.UUIDField(default=uuid.uuid4, editable=False, unique=True),
)
# ... mismo patrón para AsignacionRol.cloud_id, lineas 39-43
```

**Por qué falla siempre, no solo en esta BD:** al agregar una columna con
`unique=True` y un `default` que es una función Python (`uuid.uuid4`) sobre
una tabla con filas existentes, Postgres/Django evalúa el default **una sola
vez** para el `ALTER TABLE ADD COLUMN`, así que **todas las filas
preexistentes reciben el mismo UUID**. La creación del índice único that sigue
falla en cuanto hay 2+ filas. En esta copia había exactamente 2 roles
(`Administrador`, `Cajero`) y 4 asignaciones — el mínimo que deja
`bootstrap_negocio` en **cualquier instalación real**, incluidas Royal Plast y
SK Performance. Esto no es un defecto de esta BD de desarrollo: es
determinístico y va a fallar igual en la primera actualización real que
alguien intente con este candidato.

**La propia base de código ya conoce y documenta el arreglo correcto** — dos
migraciones distintas resuelven exactamente este mismo problema con el patrón
de tres pasos (columna nullable sin unicidad → `RunPython` que asigna un UUID
por fila → `AlterField` que recién ahí impone unicidad/`NOT NULL`):

- `apps/caja/migrations/0003_caja_origen_id.py:10-16` — el docstring lo explica
  en las mismas palabras que este hallazgo: *"un campo unico con default no se
  puede agregar de una sobre filas existentes: `uuid.uuid4` se evaluaria una
  sola vez y todas las cajas quedarian con el MISMO valor"*.
- `apps/sync/migrations/0011_transporte_durable_bug_k.py:6-11,21-71` — mismo
  patrón para `EventoSync.event_id` (con `RunPython poblar_event_ids`).

Verificado empíricamente que ninguna otra migración de las 32 pendientes tiene
el mismo defecto: `auditoria.0008` también hace `AlterField` con
`default=uuid.uuid4, unique=True` sobre `Auditoria.event_id`
(`apps/auditoria/migrations/0008_...py:216-220`), pero esa migración **sí
aplicó limpio** en esta misma corrida (`showmigrations auditoria` → `[X]
0008`) porque `event_id` ya venía poblado con valores distintos por fila desde
una migración anterior de esa misma app — no es el mismo caso, es solo
endurecer metadata sobre una columna ya correcta.

**Impacto:** con el candidato tal como está empaquetado hoy, `actualizar.bat`
(o cualquier `manage.py migrate` manual) se detiene a mitad de camino en
`permisos.0011` en cualquier tienda real. `Rol`/`AsignacionRol` quedan sin
`cloud_id`/`revision`/`deleted_at`/`origen_cloud` — bloqueando CT-02 (`rbac.
sync.v2`) y todo lo que dependa de esos campos — pero, como se ve abajo, la
transacción de Django protege que esto no deja al negocio con una BD a medio
migrar de forma insegura.

**No corregido por mí** — `apps/permisos` es propiedad de Codex/A y el encargo
de C06 es reportar, no reparar el núcleo del otro agente. Recomendación
concreta (mismo patrón ya usado dos veces en este repo): dividir la migración
en tres pasos para `Rol.cloud_id` y `AsignacionRol.cloud_id` igual que hace
`caja.0003`.

## Rollback con datos reales — verificado, no solo intentado

Gracias a que Django ejecuta cada migración en su propia transacción sobre
PostgreSQL, el `IntegrityError` de `permisos.0011` revirtió **solo** esa
migración — no dejó columnas a medio agregar. Aun así, se ensayó el rollback
completo vía backup/restore, no solo se confió en la transacción:

1. **Huella antes de restaurar:** `showmigrations permisos` mostraba `0008`
   como la última aplicada (`0009`/`0010`/`0011` sin aplicar) — ese es el
   estado real de fábrica de `pos_fifo_db`, antes de que esta corrida
   avanzara nada.
2. `DROP DATABASE pos_c06_1_lab` + `createdb` (simula perder por completo la
   BD de laboratorio, el escenario más duro de recuperación).
3. `pg_restore` desde el backup del paso 1 de este documento.
4. **Huella después:** vía ORM (`Rol.objects.count()`, `AsignacionRol.objects.
   count()`, `Producto.objects.count()`, `Venta.objects.count()`) → **2 / 4 /
   89 / 45**, idéntico a antes de empezar. `showmigrations permisos` volvió a
   mostrar exactamente `0008` como último aplicado — ni una migración de más
   ni de menos.

**Resultado: restauración verificada por conteo real de filas y por estado de
migraciones, no solo "el comando no dio error".** `pos_fifo_db` (el original)
nunca se tocó en ningún punto de este ensayo — todo el riesgo lo absorbió la
copia `pos_c06_1_lab`.
